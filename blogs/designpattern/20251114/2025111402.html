单例模式深度解析：从入门到Spring实战

mingdada2025-11-14 20:00:00设计模式设计模式

上一篇：《什么是 UML 类图》

在软件开发中，我们经常会遇到这样的场景：线程池、缓存、日志对象、对话框、打印机驱动程序等。这些对象如果被创建多个实例，可能会导致资源耗尽、行为不一致等问题。因此，我们希望确保一个类在任何情况下都只有一个全局唯一的实例，并提供访问该实例的全局节点。这就是单例模式（Singleton Pattern）的用武之地。

一、 单例模式的核心思想

意图： 保证一个类仅有一个实例，并提供一个访问它的全局访问点。

关键点：

  • 1.私有化构造方法：防止外部通过 new 关键字创建实例。

  • 2.内部创建唯一实例：由类自己负责创建自己的唯一实例。

  • 3.提供公开的静态访问方法：允许外部代码获取这个唯一实例。

二、 实现方式的演进与线程安全之争

单例模式的实现方式多种多样，其演进史本质上是一部与“线程安全”和“性能”斗争的历史。主要分为两大派系：饿汉式 和 懒汉式。

1. 饿汉式（Eager Initialization）

“饿汉”很着急，类一加载就立即创建实例。

public class EagerSingleton {
    // 1. 在类加载时立即创建唯一实例
    private static final EagerSingleton INSTANCE = new EagerSingleton();

    // 2. 私有构造器，堵死外部创建的路
    private EagerSingleton() {
        // 防止通过反射调用构造器
        if (INSTANCE != null) {
            throw new RuntimeException("单例对象不能重复创建");
        }
        System.out.println("EagerSingleton 实例被创建了");
    }

    // 3. 提供全局访问点
    public static EagerSingleton getInstance() {
        return INSTANCE;
    }
}

优点：

  • 实现简单，代码清晰。

  • 线程安全：由于实例在类加载初期就已经创建，由JVM保证其线程安全性。

缺点：

  • 可能造成资源浪费：如果这个实例非常占用资源，但在整个程序运行过程中从未被使用过，那它就是不必要的开销。

2. 懒汉式（Lazy Initialization）及其线程安全问题

“懒汉”很懒，只有在真正需要的时候才创建实例。

基础版（非线程安全）

public class UnsafeLazySingleton {
    private static UnsafeLazySingleton instance;

    private UnsafeLazySingleton() {}

    public static UnsafeLazySingleton getInstance() {
        // 如果实例为空，则创建
        if (instance == null) {
            // 模拟多线程环境下，第一个线程在此处挂起
            try {
                Thread.sleep(10);
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
            instance = new UnsafeLazySingleton();
        }
        return instance;
    }
}

问题： 在多线程环境下，如果两个线程同时执行到 if (instance == null) 判断，且都判断为 true，那么它们都会执行 new 操作，从而创建出多个实例，违反了单例原则。

线程安全版（方法同步）

public class SynchronizedLazySingleton {
    private static SynchronizedLazySingleton instance;

    private SynchronizedLazySingleton() {}

    // 使用 synchronized 关键字修饰方法
    public static synchronized SynchronizedLazySingleton getInstance() {
        if (instance == null) {
            instance = new SynchronizedLazySingleton();
        }
        return instance;
    }
}

优点： 通过 synchronized 保证了线程安全。

缺点： 性能差。每次调用 getInstance() 都需要进行同步，而实际上只有在第一次创建实例时才需要同步。后续的调用都是直接返回实例，此时的同步锁就成了不必要的性能开销。

3. 双重检查锁（Double-Checked Locking）

为了解决懒汉式同步方法的性能问题，双重检查锁应运而生。

public class DCLSingleton {
    // 关键：使用 volatile 关键字修饰
    private static volatile DCLSingleton instance;

    private DCLSingleton() {}

    public static DCLSingleton getInstance() {
        // 第一次检查：如果实例已存在，直接返回，避免进入同步块。
        if (instance == null) {
            // 同步代码块
            synchronized (DCLSingleton.class) {
                // 第二次检查：进入同步块后再次检查，防止在等待锁期间已有线程创建了实例，就会产生多个实例
                if (instance == null) {
                    instance = new DCLSingleton();
                }
            }
        }
        return instance;
    }
}

为什么需要 volatile 关键字？ instance = new DCLSingleton(); 这行代码并非原子操作，它大致分为三步：

  • 1.为对象分配内存空间。

  • 2.初始化对象（调用构造方法等）。

  • 3.将 instance 引用指向分配的内存地址。

JVM 可能会进行指令重排序，导致步骤2和步骤3的顺序颠倒。如果线程A执行了1和3，但尚未执行2，此时 instance 已不为 null。如果线程B此时调用 getInstance()，第一次检查发现 instance != null，就会直接返回一个尚未初始化完成的对象，从而导致程序错误。

volatile 关键字的作用：

  • 禁止指令重排序：确保 instance = new DCLSingleton(); 的操作按1->2->3的顺序执行。

  • 保证变量的可见性：一个线程修改了 volatile 变量，新值会立刻被其他线程看到。

因此，volatile 是双重检查锁模式正确工作的必要条件。

没有二次校验会出现的问题

public class DCLSingleton {
    // 关键：使用 volatile 关键字修饰
    private static volatile DCLSingleton instance;

    private DCLSingleton() {}

    public static Singleton getInstance() {
        if (instance == null) {  // 第一次检查
            synchronized (Singleton.class) {
                // 如果没有第二次检查，会有什么问题？
                instance = new Singleton();  // 直接创建实例
            }
        }
        return instance;
    }
}

多线程场景分析 假设有两个线程 Thread A 和 Thread B：

时间线分析：

时间点Thread AThread B
t1进入getInstance()
t2第一次检查: instance == null ✅
t3获得锁(synchronized)
t4开始创建实例进入getInstance()
t5正在创建实例...第一次检查: instance == null ✅ (因为A还没创建完)
t6正在创建实例...等待锁(因为A持有锁)
t7创建完成，释放锁
t8获得锁
t9❌ 如果没有二次检查：会再次创建实例！
t10释放锁

结果：单例被创建了两次，违反了单例模式的原则！

4. 静态内部类实现（推荐）

这是一种比双重检查锁更简洁、优雅的实现方式，它利用了JVM的类加载机制。

public class InnerClassSingleton {
    
    private InnerClassSingleton() {}

    // 静态内部类
    private static class SingletonHolder {
        // 在内部类中持有外部类的唯一实例
        private static final InnerClassSingleton INSTANCE = new InnerClassSingleton();
    }

    public static InnerClassSingleton getInstance() {
        // 只有当调用此方法时，JVM才会加载 SingletonHolder 类并创建 INSTANCE
        return SingletonHolder.INSTANCE;
    }
}

原理：

当外部类 InnerClassSingleton 被加载时，其静态内部类 SingletonHolder 并不会被加载。

只有当显式调用 getInstance() 方法时，才会触发JVM加载 SingletonHolder 类。

JVM在加载类的过程中是天然的线程安全的，从而保证了 INSTANCE 被唯一且安全地创建。

优点：

  • 懒加载：只有在需要时才创建实例。

  • 线程安全：由JVM保证。

  • 实现简洁，无需同步锁，性能高。

5. 枚举实现（《Effective Java》强烈推荐）

这是实现单例模式的最佳方式，从Java 1.5开始支持。

public enum EnumSingleton {
    INSTANCE; // 这就是单例的实例

    // 可以添加任意的方法和属性
    private String data;

    public String getData() {
        return data;
    }

    public void setData(String data) {
        this.data = data;
    }

    public void doSomething() {
        System.out.println("枚举单例的方法被执行");
    }
}

// 使用方式：
// EnumSingleton instance = EnumSingleton.INSTANCE;
// instance.doSomething();

为什么是最佳实践？

  • 绝对防止多实例创建：枚举实例的创建是线程安全的，并且由JVM从根本上保证只会被初始化一次。

  • 天生支持序列化：普通的单例类在序列化和反序列化时，可能会创建新的实例。而枚举单例由JVM保证序列化的安全性。

  • 防止反射攻击：反射机制无法通过构造方法创建枚举实例，这从根本上杜绝了通过反射破坏单例的可能。

三、 实战：Spring框架中的单例

在Spring框架中，单例模式被运用得淋漓尽致，但其scope（作用域）与我们上面讨论的略有不同。

Spring Bean的默认Scope：Singleton

在Spring的IoC容器中，默认情况下，每个被管理的Bean都是单例的。

@Component // 或者 @Service, @Repository 等
public class MyService {
    // ...
}

当你通过 @Autowired 注入 MyService 时，Spring容器在整个应用生命周期内，始终会返回同一个 MyService 实例。

Spring单例 vs 设计模式单例

  • 设计模式单例：一个JVM内，一个类加载器下，保证只有一个实例。

  • Spring单例：一个Spring IoC容器（ApplicationContext）内，保证只有一个Bean实例。如果你有多个容器，或者在一个容器中有多个类加载器，则可能存在多个“单例”实例。

Spring中的懒加载

Spring也支持懒加载模式，对应于我们之前讲的“懒汉式”。

@Component
@Lazy // 添加此注解，表示这个Bean是懒加载的
public class LazyService {
    public LazyService() {
        System.out.println("LazyService 被初始化了！");
    }
}

只有当第一次被注入或通过容器显式获取时，LazyService 的实例才会被创建。

Spring ApplicationContext 本身也是单例

在典型的Spring Boot应用中，我们通常通过 SpringApplication.run(...) 启动一个 ApplicationContext。这个上下文对象本身在应用中就是作为单例存在的，它是我们获取所有Bean的根工厂。

总结

实现方式线程安全懒加载防止反射/序列化破坏推荐度
饿汉式✅❌❌★★★☆☆
同步方法懒汉式✅✅❌★★☆☆☆
双重检查锁✅✅❌★★★☆☆
静态内部类✅✅❌★★★★☆
枚举✅❌✅★★★★★

选择建议：

  • 如果对资源消耗不敏感，或者实例初始化非常快，饿汉式是最简单的选择。

  • 如果需要懒加载，并且不担心反射和序列化攻击，静态内部类是实现是最优雅的。

  • 如果追求极致的安全性和简洁性，尤其是在分布式或复杂的反射环境中，请毫不犹豫地选择枚举实现。

  • 在Spring生态中，充分利用其容器管理的单例Bean，并根据需要使用 @Lazy 注解控制加载时机。

  • 单例模式看似简单，但其背后隐藏着深厚的并发编程、类加载机制和内存模型的知识。理解其各种实现的原理与权衡，是每一位Java开发者迈向高级阶段的必经之路。
